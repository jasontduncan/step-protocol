# RFC 0001: Harden STEP Core

- Status: Draft, non-normative
- Created: 2026-07-19

## Premise

STEP's core model—stable task identity, explicit state, and durable evidence—has
survived substantial use. That use also exposed questions the current protocol
does not answer precisely enough for independent implementations to reach the
same conclusions.

This RFC proposes a hardening boundary, not an immediate rewrite.

## Evidence boundary

An internal audit of a private, production-scale development corpus found 2,218
current STEP step records across 10 WorkNodes. Its history included continuation
after context compaction, runner and test failures, blocked work, metadata loss,
branch divergence, and worktree reconciliation.

The source codebase has no current users. The repository is private, the audit
is not independently reproducible, and historical artifacts span changing
conventions. This evidence supports STEP's usefulness in one corpus; it does not
establish universal conformance, correctness, enterprise certification, or
business impact.

## Boundary

STEP Core should own only portable semantics:

- WorkNode discovery and required artifacts
- stable phase, step, and label identity
- PLAN and STATE consistency
- lifecycle and actionable-step selection
- evidence association
- recovery and non-destructive reconciliation
- versioning, extensions, and conformance
- trust boundaries

Execution profiles may add stronger policy:

- worker and runner write boundaries
- test and approval gates
- transcript capture
- finish-only recovery
- commits, branches, worktrees, locks, and dependency routing

A profile may strengthen Core but must not redefine it. Profile artifacts must
remain distinguishable from Core artifacts.

## Questions before 1.0

| Area | Question |
| --- | --- |
| Grammar | What identifier, Unicode, case, table, and path rules can every reader implement safely? |
| Lifecycle | Which transitions are valid, and how are blocked, manual, migrated, and superseded outcomes represented? |
| Durability | Must `in-progress` be durably observable, or may one atomic run persist `todo -> done`? |
| Evidence | How are canonical logs distinguished from transcripts, tests, screenshots, and retained history? |
| Authority | What wins when runner state, STATE, logs, and version-control history disagree? |
| Recovery | How is a partial multi-file update detected and reconciled without erasing conflict? |
| Selection | Should order follow PLAN position, a sortable identifier, or another canonical rule? |
| Concurrency | What observable rule prevents two writers or duplicate active ownership after a node split? |
| Migration | How are legacy, reconstructed, copied, and orphaned artifacts preserved without becoming active work? |
| Versioning | How does a WorkNode declare its protocol revision and required extensions? |
| Trust | How does STEP keep untrusted logs and imported evidence from redefining executable intent? |

## Cases the rules must resolve

These cases were reduced from observed history. Names, paths, code, customers,
and product details are omitted.

| Case | Required property |
| --- | --- |
| Runner metadata outside worker scope | Classify runner mutation separately and preserve completed implementation |
| Test failure after worker success | Block acceptance without discarding the change set |
| Finish-only recovery | Resume finalization without a second implementation pass or duplicate effects |
| Lost untracked metadata | Recover only evidenced facts and identify irrecoverable detail |
| Context compaction | Let a fresh session resume the same step from durable artifacts |
| WorkNode split | Preserve copied history while retaining one active owner |
| Hyphenated semantic identifiers | Parse and round-trip identity without path ambiguity |
| Blocked dependency | Preserve the blocked interval and reason after later completion |
| Stale runner state | Report conflict and reconcile by a normative precedence rule |
| Transcript sidecars | Distinguish sidecars from canonical logs or provide a migration path |
| Manual completion | Record provenance without inventing a runner event |
| Worktree reconciliation | Preserve identity and history while making conflicts explicit |

## Acceptance

RFC 0001 is ready to affect `PROTOCOL.md` only when:

- identifier and path grammar are machine-testable;
- lifecycle, selection, and precedence rules are explicit;
- partial-update recovery has a deterministic result;
- Core and profile artifacts are distinguishable;
- legacy migration preserves evidence without inventing history;
- two independent readers agree on the same fixture corpus.

Until then, this document is a request for hostile readings and independent
implementation attempts. `PROTOCOL.md` remains the authority.
