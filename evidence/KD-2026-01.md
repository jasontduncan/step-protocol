# Case Study KD-2026-01

- Status: Internal repository audit, anonymized summary
- Audit date: 2026-07-19
- Snapshot: private repository at `cc7a062c`
- Independence: not independently certified

## Scope

The source is a private, multi-application software codebase under active
development. It has no current users. “Production-scale” in this document
describes engineering scope and operational discipline, not deployment,
customer adoption, revenue, or enterprise certification.

The product name, domain, paths, source code, customer details, and
security-sensitive architecture are withheld. `KD-2026-01` is a stable case
identifier and does not imply a public product name.

## Method

The audit performed a read-only inspection of current WorkNodes, execution
artifacts, retained transcripts, and version-control history at the snapshot
above. Counts represent current PLAN/STATE rows, not deduplicated business work
items. Historical moves, copies, migrations, and orphaned artifacts can make raw
log counts differ from current row counts.

Because the repository is private, this public summary is not independently
reproducible. Supporting commands and artifact references are retained privately
for later review or controlled disclosure.

## Population

The snapshot contained:

- 10 current WorkNodes;
- 2,218 current PLAN/STATE step records;
- 2,172 `done` rows;
- 39 `superseded` rows;
- 2 `in-progress` rows;
- 5 `todo` rows;
- approximately 1,954 Markdown files in associated log directories;
- 526 retained `.stdout` execution transcripts.

The WorkNodes included a coordinating root, large applications, services, an
edge component, and a reusable demonstration cartridge. Parallelism was
expressed through separate WorkNodes, branches, and worktrees rather than
multiple active workers mutating one WorkNode.

## Strong observations

Repository artifacts support the following bounded findings:

- sessions continued identified work after context-compaction markers;
- completed implementation survived runner finalization failures;
- an independent test failure prevented finalization after worker success;
- finish-only recovery finalized preserved work without a second implementation
  pass;
- one blocked step later completed after dependency work;
- superseded outcomes remained visible rather than being erased;
- branch and worktree reconciliation preserved stable step references;
- version-control history enabled partial reconstruction after untracked
  WorkNode metadata was lost.

The strongest evidence is not the number of rows alone. Real work failed in
several ways, remained inspectable, and was later resumed or partially
reconstructed without rewriting every failure as success.

## Important negative result

An early audit conclusion said that an auditor was failing nine of ten
WorkNodes. That conclusion was withdrawn.

The invoked program was an obsolete v0.1 static validator, not the current
runner's operational health check. It treated every file under `logs/` as a
canonical Markdown step log, so retained `.stdout` transcripts, migrated logs,
reconstructed history, and orphaned artifacts produced errors unrelated to
current operability.

The corrected conclusion was that all ten WorkNodes appeared operational, while
only one matched the obsolete validator's exact filesystem assumptions. This is
evidence of validator and protocol drift, not evidence that nine WorkNodes were
malfunctioning.

## Supported claims

This case supports statements such as:

- A private production-scale codebase has used STEP to track more than 2,200
  current step records across ten WorkNodes.
- STEP artifacts preserved resumable work through context compaction, runner
  failures, test failures, blocked work, branch divergence, and worktree
  reconciliation in this corpus.
- Separating worker completion from accepted completion allowed scope and test
  gates to stop finalization without discarding completed implementation work.
- STEP is being hardened against real execution history, including failures and
  migrations, rather than only synthetic examples.

## Unsupported claims

This case does not establish that:

- every historical WorkNode conforms to one current formal specification;
- STEP guarantees correctness or crash safety;
- STEP caused product quality or business outcomes;
- the repository proves handoff between distinct model identities;
- the codebase has production users or enterprise certification;
- an independent party has verified the audit.

## Protocol consequences

The corpus produced concrete questions about transcript sidecars, timestamp
requirements, WorkNode splits, orphan classification, state precedence,
transient `in-progress`, manual completion, identifier grammar, runner-owned
mutations, and non-destructive recovery. These questions are inputs to
[`RFC 0001`](../rfcs/0001-step-core-hardening.md) and the
[`production-derived conformance candidates`](../conformance/production-derived-cases.md).
